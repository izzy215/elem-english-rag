## 1. 문서 목적과 실행 원칙

기존 백엔드에 규칙 검색과 평가를 구현하고 `/api/fix`에 연결한다. 이 문서 하나를 공통 기준으로 관리하고, 구현은 아래 4개 실행 단위로 나누어 검증한다. 처음에는 실행 단위 ①만 요청하고, 결과를 확인한 뒤 다음 단위를 요청한다. 문서 작성과 기능 구현 완료를 구분한다.

| 실행 단위 | 작업 | 다음 단계 진입 기준 |
|---|---|---|
| ① 현황·계약·데이터 검증 | 최신 코드 확인, 데이터 검증, 임베딩 설정 결정 | 데이터 검증 통과와 연결 계약 기록 |
| ② 색인·검색 구현 | 임베딩, Chroma 저장, 공통 검색, 기존 검색 API | 재시작 후 검색 가능, 실제 후보·점수 반환 |
| ③ 검색 평가 | 검색 평가 실행기, 기존 평가 API | 실제 hit@1·hit@3와 실패 사례 확인 |
| ④ 연결 정보 인계·팀장 구현·통합 검증 | RAG 계약 인계 → 팀장 `/fix` 연결 → 공동 검증 | 응답 호환·장애 처리·기록 검증 통과 |

검색 평가를 튜터 연결보다 먼저 수행하여 검색 실패와 생성 실패를 구분한다. 정상 문장의 오교정 평가는 튜터 연결 후 수행한다. 실행하지 않은 시험이나 외부 호출을 완료했다고 보고하지 않는다.

참고: [PRD-B](../plan-B/PRD.md), [샘플 B 명세](../../data/golden/_sample-B/README.md), [데이터 계획](../plan-B/data-pipeline-plan.md), [과거 현황 분석](../plan-B/rag-pipeline-analysis-stage-1.md).

PRD는 제품 기준선이고, 현재 구현된 호출·응답 계약은 실제 코드를 우선한다. 과거 분석의 구현 상태를 현재 사실로 재사용하지 않는다. 현재 검토본은 `docs/RAG_0909/rag-implementation-work-order_v0.2.md`다(2026-09-09 `docs/RAG_0909/`로 이동됨, 최초 작성 위치는 `docs/`였음). 기존 `docs/plan-B/rag-implementation-work-order.md`는 이전 사본이다. 최종 확정 후에는 버전 접미사 없이 `docs/plan-B/rag-implementation-work-order.md`에 저장하여 기준본으로 관리한다. 이번 수정은 검토본에만 반영하며 최종본 이동·교체는 아직 수행하지 않는다.

## 2. 범위와 변경 제약

포함: 규칙 검증, 임베딩, 영속 Chroma 색인, 공통 검색 함수, `/rag/search`, `/rag/eval`, `/fix` 연결 정보 인계와 팀장 구현 후 통합 검증, 백엔드 시험과 실행 문서.

제외: 모든 프론트엔드 HTML·JS·CSS 수정, FAQ 색인과 `/ask` 연결, STT 검색 힌트 연결, `/rag/check` 실검수, `/sources`, 교재·엑셀 자동 수집, 혼합 검색·재정렬, 학생 저장 구조 전면 개편, 배포·커밋·푸시.

- `tutor.py`와 교정 프롬프트의 수정은 팀장이 수행한다. RAG 담당은 읽기·계약 제안·시험·인계만 수행하며 직접 수정하지 않는다. 출력 검증·학생 기록 처리·기록 없는 내부 교정 경로도 팀장의 구현 범위다.
- `golden.py`는 TTS 담당의 공통 로더다. 기존 함수를 사용하고 필요한 확장만 최소화한다.
- `ask.py`, `speak.py`, 생성 제공자 구현은 이번 범위에서 수정하지 않는다.
- 키는 환경설정으로만 관리하고 문서·로그·시험 출력에 노출하지 않는다.
- 다른 사람의 미커밋 변경을 보존한다. 계약을 깨는 변경이나 필수 정보가 없는 경우 해당 사항만 확인한다.

### 3.1 현재 API와 보존할 계약

베이스는 `/api`다. 기존 라우터를 사용하며 중복 엔드포인트를 만들지 않는다.

| API | 현재 입력 | 현재 반환 |
|---|---|---|
| `GET /rag/search` | `q` 필수, `level=None`, `k=3` | `{"query": q, "chunks": []}` |
| `GET /rag/eval` | 없음 | `{"n":0,"hit_at_3":null,"hit_at_1":null,"runs":[]}` |
| `POST /fix` | `text` 필수; `student="A"`, `level=2`, `unit=""`, `source="typed"` | 아래 필드 |

`/fix` 보존 필드:

```text
ok
rule: {id, name, score} | null
runner_up: {id, name, score} | null
wrong, fix, fixed, why
source: {chunk_id, text} | null
more_errors, full_fixed, suggested_questions
mission: {ok, nudge}
log_id, mode, llm
```

현재 `rule.score`, `runner_up`은 항상 `null`, `mode`는 `fallback`이다. `llm`은 생성 백엔드·모델·시간·대체 출처 정보다. 현재 공백 입력은 400, Gemini 키·규칙 누락은 500, `LLMError`는 502다. `source` 입력은 문자열이며 enum 검증은 없다. 엄격한 응답 모델도 없다.

### 3.2 PRD와의 차이 및 v0.2 방침

| 차이 | 이번 작업 방침 |
|---|---|
| PRD는 `hits`, 코드는 `chunks` | 현재 `query`, `chunks` 유지. `hits`로 일방 교체하지 않음 |
| PRD는 `kind=rule/explain/all`, 코드는 `level` | `level` 호환 유지, 최초 규칙 검색에는 필터 미적용을 명시. `kind` 도입은 후속 계약 변경 |
| PRD는 임계값 0.60 | 최초 기준선은 미설정. 실제 점수 분포 확인 후 결정 |
| PRD의 챗 파일은 `chat.py` | 실제 `ask.py`를 후속 연동 대상으로 기록 |
| 과거 작업지시서는 별도 튜터 로더 전제 | 현재 공통 `golden.py` 사용 사실 반영 |
| 과거 작업지시서는 화면 변경 포함 | 이번 v0.2는 화면 수정 제외 |

### 구현 목표 API

현재 실행 코드의 `chunks` 항목 반환·검증은 미구현이다. 다만 `rag.py` 주석에는 A안 항목 예시 `id, text, level, unit, source_page, score`가 남아 있다. 아래는 v0.2에서 제안하는 규칙 검색 항목 계약이며, 기존 구현 사실이 아니다. 기존 최상위 키는 보존하고 항목 계약은 실행 단위 ①에서 확정한다.

```json
{
  "query": "학생 입력",
  "chunks": [
    {"id": "원본 규칙 ID", "type": "규칙 유형", "text": "원본 본문", "unit": "원본 단원", "score": 0.0}
  ],
  "threshold": null,
  "score_type": "cosine_similarity"
}
```

위 점수는 형식 예시이며 실측값이 아니다. `threshold`, `score_type`은 추가 메타데이터다. 최초 버전에서 `kind`·`hits`를 필수 계약으로 도입하지 않는다.

입력 검증은 신규 구현 요구사항이다. `q`는 공백 제거 후 1~1,000자를 제안한다. `k`는 양의 정수로 검증하며 상한은 실행 단위 ①에서 결정·기록한다(현재 코드에는 범위 제한이 없고, 이전 검토본의 1~100은 코드 근거 없는 신규 제안값이었다). 실제 반환 수는 저장 건수 이하로 제한한다. 잘못된 입력은 422, 색인 없음·불일치·검색 서비스 장애는 503으로 구분한다. 오류는 기존 `{"detail":"..."}` 형식을 유지한다. 실제 빈 결과와 장애를 혼동하지 않는다.

### 완료 기준

검증·재생성·재시작·검색 시험이 통과하고 실제 후보·점수가 반환된다. 기존 API 키가 유지된다. 검색의 임계값은 아직 미설정이며 임의 값으로 정상 여부를 결정하지 않는다.

## 6. 실행 단위 ③ — 검색 평가

권장 위치: 신규 `tests/eval_rag.py`, 기존 `backend/rag.py`.

### 작업

- [ ] `golden.eval_set()`으로 평가 문장을 읽는다.
- [ ] 정답 규칙이 있는 문장의 hit@1·hit@3를 측정한다. `NONE`은 검색 적중률 분모에서 제외한다.
- [ ] 문장별 정답·후보 ID·점수·적중 여부·검색 시간·실패 이유를 저장한다.
- [ ] 검색 실패 사례를 누락하여 지표를 높이지 않는다. 전체 대상 수와 성공·실패 수를 함께 기록한다.
- [ ] 데이터·색인 해시, 임베딩 설정, 후보 수, 임계값, 실행 시각을 기록한다.
- [ ] `/rag/eval`은 저장된 검색 평가만 읽게 한다. 조회가 외부 API나 평가 실행을 유발하면 안 된다.
- [ ] 기존 `n`, `hit_at_1`, `hit_at_3`, `runs`를 유지하고 실제 실행한 이력만 `runs`에 넣는다.
- [ ] 생성 모델 비교 파일과 검색 평가 파일을 구분한다. 기존 `tests/eval_fix.py` 결과를 검색 지표로 사용하지 않는다.
- [ ] 현재 색인과 평가 해시가 다르면 이전 결과임을 식별할 수 있게 한다.

평가 API의 `n`은 오류 문장 수다. `total_n`, `normal_n`, `search_failures`, `evaluated_at`, `threshold`, `stale` 등 필요한 메타데이터를 추가할 수 있다. 미측정 지표는 `null`로 둔다. 정상 문장 오교정은 아직 미측정이며 검색 점수만으로 계산하지 않는다.

### 완료 기준

실제 hit@1·hit@3와 문장별 실패를 확인한다. hit@3 80%는 목표이며 결과를 조작하지 않는다. 현재 샘플로 설정을 조정하면 개발 평가라고 명시하고 독립 최종 성능으로 주장하지 않는다. 이 결과를 바탕으로 튜터 연결에 적합한지 판단한다.

## 7. 실행 단위 ④ — 튜터 연결·통합 검증

담당 구분: RAG 담당은 연결 정보와 평가·시험 코드를 준비한다. 팀장은 `backend/tutor.py`와 교정 프롬프트를 수정한다. 화면 수정은 양쪽 모두 이번 범위에서 제외한다.

### ④-A 연결 정보 인계 — RAG 담당

- [ ] 실제 구현된 내부 함수의 import 경로·이름·인자를 제공한다. 예정 계약 `from backend.rag import search_rules; search_rules(text, k=3)`를 구현 완료로 오인하지 않도록 실제 코드와 대조한다.
- [ ] 후보 목록의 `id`, `type`, `text`, `unit`, `score`, 정렬 순서와 점수 의미를 정의한다.
- [ ] 임계값 설정·미설정·미달 처리, 빈 결과와 장애의 차이, 예외 클래스와 호출 시간 제한을 명시한다.
- [ ] `/rag/search`, `/rag/eval`의 실제 요청·응답·오류 예시를 제공한다. `/fix`에서는 HTTP 재호출 대신 공통 검색 함수를 직접 사용하도록 안내한다.
- [ ] `/fix`의 `rule`, `runner_up`, `source`, `mode`, `fallback_reason` 필드 매핑과 전체 규칙 대체 정책을 제공한다.
- [ ] 정상 검색·장애·근거 밖 ID 시험 사례와 기록 없는 내부 교정 함수에 필요한 입력·출력 계약을 제안한다.
- [ ] 인계 정보를 이 문서의 진행 기록에 기록하거나, API 인터페이스 정의서가 있으면 해당 절을 참조한다. 별도 메시지 전송은 사용자 요청 없이 하지 않는다.

④-A 완료와 ④ 전체 완료는 다르다. 팀장 변경이 아직 없으면 상태를 “인계 완료·팀장 구현 대기”로 기록한다. RAG 담당이 대신 구현하거나 교정 평가를 mock 결과로 완료 처리하지 않는다. 팀장 구현 완료가 전달되면 현재 코드·계약을 확인한 뒤 ④-C를 재개한다.

### ④-B 검색 연결 — 팀장 구현 요구사항

- [ ] `_search_rule()`의 스텁을 공통 검색 호출로 교체하고 후보 목록·점수·차순위를 보존한다.
- [ ] 상위 3개를 검색하되 최초 기준선은 1위 규칙만 생성 근거로 전달한다.
- [ ] `id`, `type`, `text`를 유지해 기존 `_rules_block()`과 연결한다.
- [ ] 검색 장애 또는 설정된 임계값 미달 시 검증된 전체 규칙으로 전환한다. 낮은 유사도를 정상 문장으로 단정하지 않는다.
- [ ] 기존 `llm.generate_json()`, 미션 판단, 단일 교정, 학생 기록 흐름을 유지한다.
- [ ] 실제 검색 근거 사용은 `mode="rag"`, 전체 규칙 사용은 `mode="fallback"`로 구분한다.
- [ ] `rule.score`, `runner_up`을 실제 검색 결과에서 구성한다. 전체 규칙 모드는 점수·차순위 `null`을 유지한다.
- [ ] `source`는 실제 전달 규칙에서 만들고 모델이 작성한 출처를 신뢰하지 않는다.
- [ ] 추가 필드 `fallback_reason`으로 검색 대체 이유를 기록한다. 생성 백엔드 대체 정보 `llm.fallback_from`과 구분한다.

### 출력·기록 검증 — 팀장 구현 요구사항

- [ ] 입력과 근거의 명령문을 시스템 지시로 취급하지 않도록 프롬프트 구획을 구분한다.
- [ ] JSON 객체 여부·필수 필드·자료형·정상 판정과 교정 필드의 일관성을 검증한다.
- [ ] 규칙 ID가 실제로 전달한 후보에 포함되는지 검사한다. 전체 골든 목록에 존재하는지만 확인하지 않는다.
- [ ] 없는 ID를 `ok=true`로 바꾸는 현재 처리를 제거한다. 잘못된 출력은 502 등 명시적인 오류로 처리한다.
- [ ] `wrong`이 원문에 존재하는지와 단일 교정 결과를 검증한다. 오류 결과를 학생 기록에 저장하지 않는다.
- [ ] 검색도 전체 규칙도 사용 불가하면 503으로 구분한다. 생성 실패는 무한 재시도하지 않는다.
- [ ] 3.1절의 기존 `/fix` 응답 필드와 자료형을 보존한다. 다만 근거를 1위 규칙으로 줄이면 판단 범위가 좁아지므로 의미까지 동일하다고 보고하지 않는다. 아래 판단 범위 정책을 적용한다.

현재 `/fix`의 Gemini 키 사전 검사는 다른 생성 백엔드 사용도 차단할 수 있다. 이를 인계 사항으로 보고하고 이번 RAG 작업에서 제공자 로직 전반을 개편하지 않는다.

### 판단 범위와 복수 오류 정책

현재 프롬프트는 `full_fixed`를 참고 규칙 기준으로 전부 고친 문장으로 정의한다. 전체 규칙에서 1위 규칙만 전달하는 방식으로 바꾸면 판단 범위도 줄어든다.

- `ok=true`는 전달 근거 범위에서 교정할 오류를 찾지 못했다는 뜻이다. 문장 전체의 정확성을 보장하지 않는다.
- `more_errors`는 전달한 근거로 확인한 추가 오류 여부다. 다른 규칙의 오류가 없다는 보장이 아니다.
- `full_fixed`는 전달한 근거 범위에서 확인한 오류를 모두 고친 문장이다. 전체 문법 오류를 고친 최종 정답으로 보장하지 않는다.
- 검색 1위만 전달하는 기준선에서 전체 규칙 기반 교정과 동일한 복수 오류 탐지 성능을 완료 조건으로 요구하지 않는다. 같은 규칙의 복수 오류와 서로 다른 규칙의 복수 오류를 나누어 시험하고 한계를 보고한다.
- 전체 규칙 범위의 최종 교정이 필요하면 후보 확대 또는 별도 전체 규칙 검토 경로를 팀장과 결정한다. 이번 기준선에 임의로 추가하지 않는다.
- 현재 화면의 “잘 썼어요”, “다 고치면 이렇게 돼요” 문구는 이 제한을 표현하지 않는다. 화면은 수정하지 않고 팀장에게 인계하며, 화면까지 의미가 검증되었다고 보고하지 않는다.

### ④-C 교정 평가·통합 검증 — 팀장 구현 후 RAG 담당과 공동 확인

- [ ] 정상 문장은 실제 교정 로직을 통과시켜 불필요한 교정 여부를 측정한다.
- [ ] 기록 없는 내부 교정 경로로 평가하여 학생 로그·오답노트를 오염시키지 않는다. 공개 API에 기록 해제 옵션을 추가하지 않는다.
- [ ] 생성 실패·형식 오류는 정상 유지로 집계하지 않는다.
- [ ] 평가 결과에 프롬프트·생성 모델 설정과 정상 문장 평가 건수·오교정·생성 실패를 별도 기록한다.
- [ ] `/rag/eval`에 생성 미측정과 측정 완료 상태가 구분되게 추가 결과를 제공한다.

### 완료 기준

인계 계약과 팀장 구현 완료 증거가 있어야 한다. RAG 담당은 통합 검증 중 발견한 튜터·교정 프롬프트 결함을 팀장에게 전달하고 해당 파일을 직접 수정하지 않는다. 미수정 결함과 미검증 조건은 남은 작업으로 기록한다.

실제 검색을 사용한 `/fix` 응답의 모드·근거·점수가 일치한다. 잘못된 출력과 장애가 정상 판정으로 바뀌지 않는다. 기존 응답 호환과 학생 기록 검증이 통과한다. `/fix` 15초 이내는 목표이며 실측 전 보장하지 않는다.
