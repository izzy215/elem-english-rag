## 1. 작업 목표

0909 회의에서 정한 목표는 실데이터 38개 규칙과 72개 평가 문장으로 RAG 검색 오류 원인을 분석하고, `hit@1`을 75% 이상으로 개선하는 것이었다.

평가 정답은 검색 결과에 맞춰 수정하지 않고, 골든 데이터의 정답을 기준으로 검색 품질을 측정했다. `patterns.csv`는 정답 유출을 막기 위해 임베딩 대상에서 제외했다.

## 2. 기준선 분석

초기 Chroma 기본 임베딩은 로컬 `all-MiniLM-L6-v2` 모델을 사용했다.

- 임베딩 차원: 384
- 평가 대상: 오류 문장 65개, 정상 문장 7개
- 검색 실패: 0건
- `hit@1`: 70.77%
- `hit@3`: 87.69%

주요 미스 케이스는 다음 네 유형으로 분류됐다.

1. R-01 형용사 앞 be동사 누락이 규칙 설명의 표현 범위 밖으로 빠짐
2. R-08 단수·복수 지시어와 R-05/R-12 관련 규칙이 개념적으로 혼동됨
3. R-35 전체 현재진행형과 R-17 특수 규칙처럼 규칙 정의가 겹침
4. `want`, `the park`, `under the table`처럼 문장 속 내용어가 다른 규칙을 강하게 끌어오는 현상

또한 `nice meet you` 사례에서는 필요한 to부정사 규칙이 검색 후보에 없어, LLM이 가장 가까운 다른 규칙을 선택하는 규칙 누락 문제도 확인했다. 이는 검색 순위 문제와 별도로 관리해야 한다.

## 3. 개선 실험

### Top-K 비교

`hit@1`은 1위만 보는 지표이므로 K를 늘려도 개선되지 않는다. `hit@3`에서 `hit@5`로 늘렸을 때는 1건만 추가 회복되어 효과가 작았다.

- K=1: `hit@1 70.77%`
- K=3: `hit@3 87.69%`
- K=5: `hit@5 89.23%`

따라서 단순히 후보 수를 늘리는 방법은 목표 달성 수단으로 채택하지 않았다.

### 오답 예문을 포함한 로컬 임베딩

`errors.jsonl`의 규칙별 오답 예문을 임베딩 본문에 추가해 비교했다. 예문 5개를 추가했을 때 `hit@1 72.31%`로 일부 개선됐지만 목표 75%에는 도달하지 못했다. 예문을 10개까지 늘리면 오히려 변별력이 떨어졌다.

### Gemini 임베딩

실데이터 38개 규칙 전체에서 `gemini-embedding-001`을 비교했다.

- 임베딩 차원: 3072
- `hit@1`: 76.92%
- `hit@3`: 89.23%
- 검색 실패: 0건

로컬 모델보다 `hit@1`이 6.15%p 높았고, 기준 목표 75%를 넘긴 유일한 검증 경로였다. 다만 Gemini API 호출 비용, rate limit, 네트워크 장애, 쿼리 지연시간이라는 운영 위험이 있다.

## 5. 남은 문제와 결론

Gemini 임베딩은 기존 골든 평가셋 기준 목표를 달성했지만, 모든 새로운 문장에서 75% 이상을 보장하지는 않는다. 홀드아웃 30문장 실험에서는 `hit@1 66.67%`, `hit@3 91.67%`로 확인됐다.

다음 문제는 임베딩 모델만으로 해결되지 않는다.

- R-01: `He tired after school.`, `He hungry now.` 같은 표현을 규칙 데이터가 충분히 대표하지 못함
- R-08/R-05/R-12: 단수·복수 규칙의 개념 경계가 겹침
- R-35/R-17: 일반 규칙과 특수 규칙의 정의가 겹침
- 필요한 규칙이 골든 규칙 목록에 없는 문장은 검색 모델을 바꿔도 해결할 수 없음
- Gemini 임베딩 운영 시 rate limit과 비용 정책이 필요함

최종 판단은 **검색 임베딩은 Gemini로 적용하고, 생성 모델은 로컬 Ollama로 분리 운영**하는 것이다. 이후 개선은 모델 교체보다 규칙 데이터 보강, 규칙 간 경계 정리, API 호출 캐시·rate limit 대응을 우선한다.
