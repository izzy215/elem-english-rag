## 1. 한 줄 정의

> 초등학생이 Unit 미션에 맞춰 **영어 문장을 말하거나 쓰면**, RAG가 우리가 만든 문법 규칙 조각에서 관련 규칙을 찾아 **AI가 근거를 붙여 고쳐주고**, 틀린 규칙이 오답노트에 쌓여 연습으로 이어지는 튜터.

핵심 루프: **표현 익히기 → 내 문장 말하기/쓰기 → RAG 규칙 검색 → 고쳐주기 + 설명 → 오답노트(문법) → 규칙 연습 → 다시 말하기**

A안과의 차이 한 줄: A는 "단어 4지선다 → 오답 단어 복습", B는 "내 문장 → 문법 규칙 진단". **B에서만 RAG가 진짜 검색을 한다** (학생 문장에는 규칙 라벨이 없으므로).

## 2. 왜 B인가

- **RAG가 필수인 구조.** 학생이 말한 문장은 데이터에 없고 라벨도 없다. 어느 규칙인지 검색으로 찾아야 한다. A안의 "단어 id → 조각"은 DB 조회였다.
- **팀원 작업이 핵심에 들어온다.** STT(완성)가 튜터의 입력, TTS가 패턴 듣기.
- **데이터팀 샘플과 일치.** 그들이 만든 `retrieved_context`가 규칙 조각, `student_error`가 오류 예시.
- **발표 장면이 강하다.** 🎙 말하기 → 검색 점수 → 고침 → 근거. "언제 DB고 언제 RAG인지 구분했다"까지 말할 수 있다.

### 2.1 RAG의 역할 정의 (A·B 공통 전제 → [docs/README](../README.md))

초등 영어는 답이 정해져 있다. 고정되지 않은 것은 **질문**(학생이 쓴 문장, 삐뚤빼뚤한 물음)이다.
- **깔때기**: 라벨 없는 학생 문장 → 올바른 규칙 조각. hit@3 가 재는 것.
- **목줄**: 고쳐주기·설명은 검색된 조각 안에서만. 아이에게 틀린 문법을 가르치지 않기 위한 보증.
- 한계: 이 규모에선 키워드 검색과 차이가 작을 수 있음. 발표 문장 — *"닫힌 도메인에서 RAG의 역할은 지식 확장이 아니라 질문 흡수와 근거 보증이다."*
- 로드맵: 열린 문제(자유 작문 첨삭)는 다음 단계.

## 6. 시스템 구성

```
브라우저 (HTML + JS, 화면별 파일)
   │ /api/...
FastAPI
   ├─ golden.py    levels · units · words · patterns · faq     TTS 담당
   ├─ rag.py       /rag/search · /rag/eval (Chroma 검색)         RAG 담당  ★
   ├─ indexing.py · embedding.py   색인 생성(--rebuild) · gemini-embedding-001   RAG 담당
   ├─ tutor.py     /fix (검색 + 후보 규칙 + LLM + 서버 검증)     팀장     ★
   ├─ llm.py       LLM 스위치 (gemini | claude | 로컬 엔드포인트, 폴백)  팀장
   ├─ ask.py       /ask (FAQ 매칭 + LLM) 물어보기 챗              TTS 팀원
   ├─ admin.py     /admin/golden · /admin/log (관리자)           팀장   (BigQuery 리포트는 미착수)
   ├─ student.py   오답노트 · 문장 로그 · /notebook              팀장
   ├─ drill.py     규칙 연습 문제 · /drill · /drill/answer      팀장
   ├─ tts.py · speak.py (+ whisper_server.py 로컬 Whisper)      TTS 담당 (완성)
   └─ eval (tests/)  eval_rag.py 문장→규칙 hit@3 · eval_fix.py /fix 전체    RAG 담당 · 팀장
데이터
   ├─ 골든 (데이터팀 자체 제작): rules.jsonl ★ · faq.jsonl · units.csv · words · patterns · errors.jsonl · eval.csv
   ├─ 학생 DB (JSON): notebook.json · sentence_log.jsonl · drill_log.jsonl
   ├─ Chroma (data/chroma/): rules 임베딩 (gemini-embedding-001, manifest.json 이 현재 컬렉션 지정)
   └─ 음원 캐시
```

**RAG가 일하는 곳 두 군데**: ① `/fix` 안의 문장 → 규칙 검색 (구현) ② `/ask` 안의 질문 → 설명 조각 검색 (연결 예정 — 지금은 faq.jsonl 매칭). 그 외(오답노트 조회, 패턴 표시)는 id 조회이며 RAG라 부르지 않는다.

## 10. 성공 기준

- **데모 60초**: Unit 3 → 🎙 "I go to the zoo yesterday" → 고쳐줘 → 3단계 → "went" + 근거(점수 0.91) → 🙋 물어보기 "왜 went예요?" → 근거 붙은 답 → 범위 밖 질문 "오늘 저녁 뭐 먹지?"는 정중 거절 → 오답노트에 과거시제 → 학생 B로 바꾸면 비어 있음
- **숫자**: 평가셋 72문장(채점 65) 기준 **문장 → 규칙 hit@3 ≥ 80%** → 실제 **92%** (hit@1 77%), 임베딩 모델 2종 비교 그래프
- **구분 설명**: "여기는 DB 조회, 여기는 RAG"를 발표에서 명시

## 11. 리스크

| 리스크 | 대응 |
|---|---|
| 아이 발음 STT 정확도 | ⌨ 쓰기를 기본 입력, 🎙 는 데모용. 예시 문장 버튼 제공 |
| 한 문장에 오류 2개 | 점수 1위 규칙만 고치고 [고친 문장으로 다시 고쳐줘] 버튼 → 재호출, 최대 2회. 그래도 남으면 다 고친 문장을 최종 정답으로 표시 (확정) |
| 맞는 문장을 틀렸다고 함 | 점수 threshold 는 두지 않고 모델이 ok=true 로 판정 + 서버 검증(학생 단어 보존 등). 평가셋에 정상 문장 7개 포함 (`/fix` 로 오탐 확인) |
| RAG 검색 늦어짐 | 1주차엔 규칙 25개 전부 프롬프트에 넣어 동작 → 검색 오면 교체 |
| 규칙 조각 품질 | 데이터 계획의 "검색 잘 되는 조각 쓰는 법" 가이드 |
