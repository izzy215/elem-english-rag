# 시연용 RAG 구현 작업지시서

작성일: 2026-09-08  
프로젝트: elem-english-rag  
주 담당: RAG 담당자  
상태: 구현 전 작업 기준입니다. 체크 항목과 실행 명령은 후속 구현을 위한 요구사항이며, 현재 동작을 보장하는 명령이 아닙니다.

## 1. 목표와 범위

`data/golden/_sample-B/rules.jsonl`의 규칙 8개를 임베딩하여 Chroma에 저장하고, 학생 문장에 관련된 규칙을 검색하여 기존 `/api/fix`와 튜터 화면에 연결합니다. 검색 근거에 따른 교정 결과와 실제 검색 점수를 표시하고, 샘플 평가셋으로 결과를 확인합니다.

기존 [PRD](PRD.md)를 제품 요구사항으로, [1단계 분석 문서](rag-pipeline-analysis-stage-1.md)를 현황 근거로 사용합니다. 이 문서는 시연 구현 범위와 구체적인 작업 순서를 정합니다.

### 포함 범위

- 샘플 규칙의 파싱·검증과 검색 조각 구성입니다.
- 임베딩, 로컬 Chroma 색인 생성과 재사용입니다.
- `/api/rag/search` 구현, `/api/fix` 검색 연결, `/api/rag/eval` 결과 제공입니다.
- 튜터·관리자 화면에서 필요한 필드 연결과 동작 검증입니다.
- 검색 평가와 정상 문장 오교정 확인입니다.

### 후속 범위

FAQ 색인과 `/api/ask`, 교재·엑셀 자동 수집, 혼합 검색, 재정렬, 운영용 인증·저장 구조는 첫 시연 범위에 포함하지 않습니다. 기존 `/rag/check`는 이번 작업으로 실제 검수 기능이 완성된 것으로 표시하지 않습니다.

## 2. 현재 코드와 변경 원칙

`rag.py`는 빈 검색 결과를 반환하고, `tutor.py`의 `_search_rule()`은 항상 `None`을 반환합니다. 현재 교정은 전체 규칙을 Gemini에 전달하는 방식입니다. 화면은 이미 `/api/fix`와 `/api/rag/eval`을 호출하므로 기존 연결을 활용합니다.

`tutor.py`는 팀장 담당 영역입니다. RAG 담당자는 검색 함수 계약과 연결 변경 내역을 공유하고, 기존 교정·미션·학생 기록 필드를 유지하는 범위에서 연결합니다. 이 문서의 구현 항목은 별도 API를 중복 생성하라는 의미가 아닙니다.

현재 `golden.py`와 `tutor.py`의 데이터 선택 방식이 다릅니다. 색인과 교정 출처가 같은 규칙을 사용하도록 공통 데이터 경로를 적용해야 합니다. 시연에서는 샘플 B를 명시적으로 선택하고 파일별로 다른 자료를 섞지 않습니다.

## 3. 표준 4단계와 전체 흐름

| 표준 단계 | 이번 구현 방식 | 주 파일 |
|---|---|---|
| ① 수집·파싱 | 제공된 JSONL을 읽고 필수 필드·자료형·중복 ID를 검사합니다. | `indexing.py`, `golden.py` |
| ② 청킹 | 규칙 한 줄을 조각 하나로 유지하고 `text`를 검색 본문으로 사용합니다. | `indexing.py` |
| ③ 임베딩·인덱싱 | 규칙 8개를 벡터로 변환하여 Chroma에 저장합니다. | `embedding.py`, `indexing.py` |
| ④ 검색·프롬프트 증강 | 학생 문장을 임베딩하여 규칙을 찾고 선택한 근거를 교정 프롬프트에 넣습니다. | `rag.py`, `tutor.py` |

```text
데이터 준비: rules.jsonl → 검증 → 조각 8개 → 임베딩 → Chroma

사용자 요청: 튜터 화면 → POST /api/fix → 규칙 검색
           → 선택 근거 + 학생 문장 + 단원 미션
           → Gemini → 응답 검증 → 근거·점수와 교정 결과 표시

평가: eval.csv → 검색 평가 / 교정 평가 → 결과 파일
     → GET /api/rag/eval → 관리자 화면
```

## 4. 설정과 데이터 계약

### 4.1 설정

| 설정명 | 작업 기준 |
|---|---|
| `RAG_DATA_DIR` | 기본값은 프로젝트 루트 기준 `data/golden/_sample-B`입니다. 색인·규칙 조회·교정이 같은 경로를 사용합니다. |
| `RAG_INDEX_DIR` | 기본값은 `data/chroma`입니다. |
| `EMBEDDING_MODEL` | 착수 시 사용 가능한 모델을 확인하여 명시합니다. 생성 모델 설정과 구분합니다. |
| `RAG_TOP_K` | 기본 후보 수는 3입니다. |
| `RAG_THRESHOLD` | 기준선에서는 미설정으로 후보를 생성 단계에 전달합니다. 점수 분포를 확인한 뒤에만 설정합니다. |
| `RAG_EVAL_DIR` | 기본값은 `data/rag_eval`입니다. |

임베딩 제공자와 모델은 현재 미확정입니다. 기존 `google-genai`를 활용할 수 있는지 먼저 확인하고, 영어 입력과 한국어 규칙의 검색 결과로 적합성을 판단합니다. 모델명·차원·문서와 질의의 처리 방식·거리 기준을 기록합니다. 구현 시 공식 문서와 실제 계정에서 호출 가능 여부를 확인하고 의존성 버전을 고정합니다.

API 키는 환경변수로만 관리하고 문서나 로그에 출력하지 않습니다. `.env.example`에는 설정명과 비밀값 없는 예시만 추가합니다.

### 4.2 조각 계약

| 필드 | 의미 |
|---|---|
| `id` | 원본 규칙 ID입니다. 예: `R-01`입니다. |
| `type` | 규칙 유형입니다. |
| `text` | 원본 검색 본문입니다. |
| `unit` | 원본 단원 값입니다. |
| `source_file` | `rules.jsonl`입니다. |
| `source_line` | 원본의 1부터 시작하는 행 번호입니다. |

`text`에는 이미 설명과 예문이 있으므로 `examples`를 다시 붙이지 않습니다. 원본 규칙 전체는 출처 확인용으로 유지합니다. 학년은 규칙에 없으므로 임의로 추가하지 않습니다. 평가 문장과 오류 예시 파일은 색인에 넣지 않습니다.

## 5. 작업별 지시와 완료 기준

### 작업 1. 준비 및 계약 확정

- [ ] 임베딩 제공자·모델과 사용 가능한 키를 확인합니다.
- [ ] 위 설정을 `backend/config.py`에 추가합니다.
- [ ] `.env.example`과 필요한 의존성을 갱신합니다.
- [ ] 색인 생성과 규칙 조회가 동일한 데이터 경로를 사용하도록 조정합니다.
- [ ] 아래 검색·API 계약을 튜터 담당자와 공유합니다.

완료 기준: 같은 설정으로 문서와 질의를 임베딩할 수 있고, 서버가 사용하는 데이터 경로가 샘플 B로 일치해야 합니다.

### 작업 2. 수집·파싱 및 청킹

대상: 신규 `backend/indexing.py`와 필요한 공통 로더입니다.

- [ ] UTF-8 JSONL을 읽고 빈 줄을 제외합니다.
- [ ] `id`, `type`, `unit`, `text`의 존재와 비어 있지 않은 문자열 여부를 검사합니다.
- [ ] 잘못된 JSON, 중복 ID, 빈 본문은 파일명과 행 번호로 보고합니다.
- [ ] 규칙 한 줄을 조각 하나로 변환합니다.
- [ ] `--validate-only` 실행 경로를 제공하여 외부 임베딩 호출 없이 검증합니다.

완료 기준: 현재 샘플에서 조각 8개를 출력하고, 잘못된 자료는 색인 생성 전에 실패해야 합니다. 검증 실패 시 기존 정상 색인은 유지합니다.

### 작업 3. 임베딩·인덱싱

대상: 신규 `backend/embedding.py`, `backend/indexing.py`입니다.

제안 함수 계약은 다음과 같습니다. 임베딩 제공자에 맞춰 내부 구현하되 호출부에는 동일한 형식을 제공합니다.

```python
def embed_documents(texts: list[str]) -> list[list[float]]: ...
def embed_query(text: str) -> list[float]: ...
```

- [ ] Chroma를 로컬 영속 저장 방식으로 구성합니다.
- [ ] 코사인 거리를 명시적으로 선택합니다.
- [ ] ID·본문·벡터·단순 자료형 메타데이터를 저장합니다.
- [ ] 데이터 해시, 모델, 차원, 본문 구성 버전과 건수를 생성 기록에 저장합니다.
- [ ] 첫 버전은 규칙 전체를 재생성하는 방식으로 구현합니다. 임시 컬렉션에 모두 저장하고 건수 확인 후 활성 색인을 전환합니다.
- [ ] 재실행으로 중복이 생기지 않고 삭제된 규칙이 남지 않게 합니다.
- [ ] 모델이나 차원 불일치 시 검색을 중단하고 재생성을 안내합니다.
- [ ] 생성된 색인과 평가 결과의 Git 제외 여부를 확인합니다.

완료 기준: 원본과 저장 건수가 모두 8개이고, 재실행·재시작 후에도 같은 조각을 조회할 수 있어야 합니다. 실패한 생성 작업이 기존 색인을 덮어쓰면 안 됩니다.

### 작업 4. 검색 함수와 검색 API

대상: 기존 `backend/rag.py`입니다.

```python
def search_rules(text: str, k: int = 3) -> list[dict]:
    """id, type, text, unit, score를 가진 후보를 유사도 내림차순으로 반환합니다."""
```

- [ ] 학생 입력을 동일한 검색 공간의 임베딩으로 변환합니다.
- [ ] 실제 후보 수가 저장 건수를 초과하지 않도록 처리합니다.
- [ ] `score = 1 - cosine_distance`로 통일하고 높은 값이 가까운 후보임을 명시합니다. 확률이나 정확도로 표현하지 않습니다.
- [ ] 단원은 첫 버전에서 강제 필터로 사용하지 않습니다. 여러 단원에서 공유하는 규칙을 누락시키지 않습니다.
- [ ] API는 내부 검색 함수를 호출하고, 튜터도 같은 함수를 직접 사용합니다.
- [ ] 검색 코드의 A안 `chunks`·FAISS 관련 설명을 현재 계약으로 정리합니다.

완료 기준: 검색 API가 실제 후보와 유한한 숫자 점수를 반환하고, 색인이 없는 상태를 정상적인 빈 결과와 구분해야 합니다.

### 작업 5. 프롬프트 증강과 `/fix` 연결

대상: `backend/tutor.py`, 필요한 경우 `backend/prompts/fix.txt`입니다.

- [ ] `_search_rule()`의 빈 구현을 공통 검색 호출로 교체합니다. 차순위를 보존할 수 있도록 검색 목록을 유지합니다.
- [ ] 최초 기준선은 상위 3개 중 1위 규칙만 기존 프롬프트 구조에 전달합니다. 후보 3개를 전달하는 실험은 기준선 평가 후 별도 기록합니다.
- [ ] `id`, `type`, `text`를 유지하여 기존 `_rules_block()`과 연결합니다.
- [ ] 학생 문장, 참고 규칙, 단원 미션을 구분하고 입력 안의 명령은 지시로 취급하지 않도록 프롬프트를 작성합니다.
- [ ] 반환 JSON의 참·거짓 값, 필수 필드와 자료형을 검증합니다.
- [ ] 오류 규칙 ID가 실제 전달한 근거에 포함되는지 확인합니다. 전체 원본에 존재하는지만 확인해서는 안 됩니다.
- [ ] `rule.score`, `runner_up`, `source`를 실제 후보에서 구성합니다. 모델이 만든 점수나 출처를 사용하지 않습니다.
- [ ] `mode`와 장애 대체 이유를 기록합니다.
- [ ] 검증에 실패한 결과는 오답노트에 저장하지 않습니다.

완료 기준: `/fix`가 실제 검색 근거를 사용해 `mode="rag"`로 응답하고 근거·점수가 일치해야 합니다. 정상 문장을 검색 점수만으로 오류 판정하면 안 됩니다.

### 작업 6. 프런트엔드 연결

대상: `frontend/js/tutor.js`, `frontend/js/common.js`, `frontend/js/admin.js`와 필요한 HTML 요소입니다.

- [ ] 기존 `fixSentence()` → `/api/fix` 흐름을 유지합니다. 튜터 화면에서 `/rag/search`를 중복 호출하지 않습니다.
- [ ] 교정 문장, 근거 ID·본문, 점수·차순위가 API 결과와 일치하는지 확인합니다.
- [ ] 화면의 고정 `0.9`는 로컬 임시 진단에서 나온 값임을 구분하고 실제 검색 시연에서 사용하지 않습니다.
- [ ] `fallback`은 정상 RAG와 구분하고 `null` 점수를 0이나 임의 값으로 바꾸지 않습니다.
- [ ] 502·503 오류를 정상 문장 또는 화면 임시 진단으로 바꾸지 않습니다.
- [ ] 관리자 데이터 경로 안내의 `_sample` 표기를 실제 `_sample-B`에 맞춥니다.
- [ ] 관리자 평가에 검색 대상 8개와 전체 10개의 차이를 명시합니다.

완료 기준: 브라우저 개발자 도구의 `/fix` 응답과 화면 내용이 일치해야 합니다. 정상 문장에서는 없는 규칙이나 점수를 억지로 표시하지 않습니다.

### 작업 7. 평가 및 관리자 API

대상: 신규 `tests/eval_rag.py`, 의미 있는 자동 시험, `backend/rag.py`입니다.

- [ ] `eval.csv`를 읽고 오류 문장 8개와 정상 문장 2개를 분리합니다.
- [ ] 오류 문장 기준 상위 1개·3개 정답 규칙 포함률을 측정합니다.
- [ ] 문장별 정답 ID, 후보 ID·점수, 적중 여부와 검색 시간을 저장합니다.
- [ ] 정상 문장은 실제 교정 경로를 평가하여 잘못 교정된 건수를 측정합니다.
- [ ] 모델 호출 실패·형식 오류는 정상 판정으로 집계하지 않고 별도 실패 건수로 기록합니다.
- [ ] 교정 평가는 일반 학생의 오답노트를 오염시키지 않도록 기록 비활성화가 가능한 내부 함수로 실행합니다. 공개 API에 기록 해제 옵션을 노출하지 않습니다.
- [ ] 데이터 해시, 색인·임베딩·프롬프트·생성 모델 설정, 후보 수, 실행 시각을 결과에 기록합니다.
- [ ] `/rag/eval`은 저장 결과만 읽습니다. 화면 조회가 임베딩이나 생성 평가를 실행하지 않습니다.

완료 기준: 모든 평가 사례의 결과 또는 실패 이유를 재현할 수 있고, 미측정 지표가 0%로 표시되지 않아야 합니다.

## 6. API 계약

아래 계약은 이번 작업에서 구현할 목표입니다. 필드 예시의 빈 목록과 `null`은 실제 측정값이 없음을 나타내며 완성 응답 예시는 아닙니다.

### 6.1 `GET /api/rag/search`

| 입력 | 규칙 |
|---|---|
| `q` | 공백 제거 후 1~1,000자입니다. |
| `kind` | 첫 버전은 `rule`만 지원합니다. 다른 값은 422로 알리고 조용히 무시하지 않습니다. |
| `k` | 1~8이며 기본값은 3입니다. |
| `level` | 기존 호환 입력으로 유지할 수 있으나 현재 색인에서는 필터링하지 않음을 명시합니다. |

```json
{
  "query": "I play with my dog yesterday.",
  "hits": [],
  "threshold": null,
  "score_type": "cosine_similarity"
}
```

`hits`의 각 항목은 `id`, `kind="rule"`, `name`, `text`, `unit`, `score`를 포함합니다. 내부 `type`을 API의 `name`으로 변환합니다. 잘못된 입력은 422, 색인 없음·불일치 또는 검색 서비스 사용 불가는 503으로 반환합니다. 오류 응답은 기존 `{"detail":"..."}` 형식을 유지합니다.

### 6.2 `POST /api/fix`

기존 입력 `student`, `level`, `unit`, `text`, `source`를 유지합니다. `text`는 1~1,000자로 제한하고 기존 공백 입력 400 처리와 자료형 검증 오류 422를 구분합니다.

| 응답 필드 | 계약 |
|---|---|
| `ok` | 선택 근거 범위에서 교정할 오류가 있는지 나타냅니다. 영어 전체의 완전한 정확성을 보장하는 값으로 설명하지 않습니다. |
| `rule` | 교정 규칙의 `id`, `name`, 실제 `score`입니다. 정상 결과는 `null`입니다. |
| `runner_up` | 검색 2위의 `id`, `name`, `score`입니다. 비교 후보일 뿐 오류 확정이 아닙니다. 후보가 없거나 전체 규칙 모드이면 `null`입니다. |
| `source` | 실제 제공된 근거의 `chunk_id`, `text`입니다. 교정 근거가 없으면 `null`입니다. |
| `mode` | 실제 검색 근거 사용 시 `rag`, 전체 규칙 사용 시 `fallback`입니다. |
| `fallback_reason` | 추가 선택 필드입니다. `search_error` 또는 `low_relevance` 등 전환 사유를 기록합니다. 일반 검색에서는 `null`입니다. |
| 나머지 필드 | `wrong`, `fix`, `fixed`, `why`, `more_errors`, `suggested_questions`, `mission`, `log_id`를 유지합니다. |

검색 장애 시 읽을 수 있는 검증된 전체 규칙 8개를 사용하는 기존 대체 처리를 유지합니다. 임계값 설정 후 관련성이 낮은 경우에도 전체 규칙 검토로 전환하고 근거 부족을 정상이라고 단정하지 않습니다. 전체 규칙 모드의 점수는 `null`로 유지합니다.

생성 실패·잘못된 JSON·근거 밖 ID는 502로 반환합니다. 규칙도 사용할 수 없으면 503으로 반환합니다. 검색·생성 호출에는 명시적인 시간 제한을 두고, 검색 제한은 전체 15초 목표보다 충분히 짧게 설정합니다. 생성 실패를 전체 규칙 모드로 무한 재시도하지 않습니다.

### 6.3 `GET /api/rag/eval`

기존 관리자 화면 호환을 위해 `n`, `hit_at_1`, `hit_at_3`, `runs`를 유지합니다. `n`은 검색 적중률의 분모인 오류 문장 수이며 현재 샘플에서는 8입니다.

```json
{
  "n": 0,
  "total_n": 0,
  "normal_n": 0,
  "hit_at_1": null,
  "hit_at_3": null,
  "normal_false_corrections": null,
  "normal_evaluated_n": 0,
  "generation_failures": 0,
  "threshold": null,
  "evaluated_at": null,
  "runs": []
}
```

이는 평가 전 응답입니다. 검색 평가 후에는 `n=8`, `total_n=10`, `normal_n=2`와 실제 검색 지표를 제공합니다. 생성 평가를 하지 않았다면 정상 문장 관련 결과는 계속 미측정으로 표시합니다. `runs`에는 실제 실행한 실험의 `label`, `hit_at_1`, `hit_at_3`를 저장합니다. 현재 색인과 평가 결과의 해시가 다르면 관리자 화면에 이전 색인 결과임을 표시합니다.

## 7. 실행 절차

아래 명령은 해당 작업을 구현한 뒤 사용할 목표 인터페이스입니다. 아직 존재하지 않는 모듈과 옵션이 포함되어 있습니다. 모든 명령은 프로젝트 루트에서 실행합니다. 활성화된 Python 3.11 이상 환경을 사용합니다.

### 7.1 검증 및 색인 생성

```powershell
Set-Location C:\elem-english-rag
python -m backend.indexing --validate-only
python -m backend.indexing --rebuild
```

예상 결과: 첫 명령은 유효 규칙 8개를 보고합니다. 두 번째 명령은 원본·저장 건수 8개와 사용한 모델·색인 식별자를 보고합니다. 같은 명령을 다시 실행해도 규칙이 16개로 늘어나지 않아야 합니다.

### 7.2 서버와 API 확인

```powershell
python -m uvicorn backend.main:app --reload --port 8000
```

별도 PowerShell에서 실행합니다.

```powershell
Invoke-RestMethod 'http://localhost:8000/api/rag/search?q=I%20play%20with%20my%20dog%20yesterday.&kind=rule&k=3'

$ragDemoBody = @{
    student = 'RAG-DEMO'
    level = 2
    unit = 'U3'
    text = 'I play with my dog yesterday.'
    source = 'typed'
} | ConvertTo-Json
Invoke-RestMethod -Uri 'http://localhost:8000/api/fix' -Method Post -ContentType 'application/json' -Body $ragDemoBody
```

검색에서는 R-01의 실제 순위를 확인합니다. 이를 보장하기 위해 결과를 하드코딩하지 않습니다. 교정에서는 `mode`, 근거 ID, 점수, 과거형 교정 여부를 확인합니다. 이 API 호출은 기존 동작대로 시연 학생의 로그를 저장합니다.

### 7.3 평가

```powershell
python -m tests.eval_rag --retrieval-only
python -m tests.eval_rag --with-generation
Invoke-RestMethod 'http://localhost:8000/api/rag/eval'
```

두 번째 명령은 외부 생성 모델을 호출합니다. 첫 번째 명령도 질의 임베딩을 외부 서비스로 구현했다면 해당 호출이 발생합니다. 생성 평가는 기록 없는 내부 교정 경로를 사용해야 합니다.

## 8. 검증 기준과 시연 절차

### 필수 기능 시험

- [ ] 잘못된 JSON·중복 ID·빈 본문을 거부합니다.
- [ ] 색인 재생성 후 변경·삭제가 반영되고 중복이 없습니다.
- [ ] 저장된 색인을 재시작 후 사용할 수 있습니다.
- [ ] 검색 결과와 프롬프트에 전달한 규칙을 추적할 수 있습니다.
- [ ] 색인 사용 불가와 생성 오류를 정해진 상태로 처리합니다.
- [ ] 근거 밖 ID와 잘못된 자료형을 교정 성공으로 처리하지 않습니다.
- [ ] 화면에 API의 실제 점수와 출처가 표시됩니다.

자동 시험에서는 임베딩·생성 응답을 대체하여 오류 처리와 연결 계약을 확인하고, 실제 검색 품질은 별도 평가 명령으로 측정합니다. 자동 시험에 매번 외부 모델을 호출하지 않습니다.

### 품질 목표

상위 3개 적중률 80% 이상은 기존 PRD의 목표입니다. 현재 오류 문장 8개에서는 최소 7개 적중이 필요합니다. 상위 1개 적중률도 함께 보고하며, 1위 근거만 사용하는 교정 기준선의 한계로 해석합니다. 정상 문장 2개는 모두 불필요한 교정이 없어야 한다는 시연 목표를 두되, 표본이 작으므로 일반 정확도로 주장하지 않습니다.

`/fix` 15초 이내는 목표이며 실측 전 보장값이 아닙니다. 실패 사례와 지연도 결과에 포함합니다. 이 샘플로 설정을 조정했다면 같은 샘플의 성능은 개발 평가라고 명시하고 독립적인 최종 성능으로 소개하지 않습니다.

### 브라우저 시연

1. 기존 시작 화면에서 학생과 Level 2·단원을 선택합니다.
2. 튜터 화면에서 `I play with my dog yesterday.`를 입력합니다.
3. `/fix` 요청이 발생하고 `rag` 모드로 답하는지 확인합니다.
4. 교정 문장, 규칙 R-01의 근거와 실제 점수를 확인합니다.
5. `She likes bananas.`를 입력하여 불필요한 교정이 없는지 확인합니다.
6. 관리자 화면에서 실제 평가값과 검색 분모 8개를 확인합니다.
7. 서버를 재시작한 뒤 같은 흐름을 반복합니다.
